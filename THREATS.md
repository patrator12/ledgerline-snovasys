# Threat model

Scope: the challenge application, its web endpoints, and the PostgreSQL database exposed through the application's restricted database role. The app is a learning prototype; see README.md for features intentionally left out.

| Threat | Control in this version | Evidence / remaining risk |
| --- | --- | --- |
| Two withdrawals race and overdraw one account | PostgreSQL row lock (SELECT ... FOR UPDATE) is held through the transaction; balance validation occurs after lock acquisition. | `tests/test_money.py::test_concurrent_withdrawals_cannot_overdraw` uses two independent sessions. The user's Docker PostgreSQL run on 2026-11-11 passed all 24 tests in 1.12 seconds. Rerun after code changes. |
| A transfer debits one account but fails before credit | Both balance changes, postings, audit entry, and idempotency result share one database transaction. | tests/test_money.py::test_transfer_balances_both_accounts_and_conserves_total. |
| A retry or double-click pays twice, or is hard to audit | Unique (actor_id, key) constraint, payload hash comparison, saved result, and an append-only replay event containing a transfer reference and key fingerprint. | tests/test_money.py::test_replayed_idempotency_key_returns_original_result_without_second_posting. The same key must be used on retry. |
| A holder names another user's account | Server checks ownership after locking the involved rows; UI filtering is only convenience. | tests/test_money.py::test_account_holder_cannot_move_someone_elses_funds. Account IDs are identifiers, not capabilities. |
| Auditor or holder escalates to an administrator action or audit view | Role checks run in the service and route; account creation is administrator-only and can assign only an active holder. Denied account-create and audit-view attempts are audited. | `tests/test_money.py::test_auditor_cannot_move_money`, `tests/test_money.py::test_account_creation_requires_admin_and_active_holder_owner`, and `tests/test_money.py::test_global_audit_log_is_admin_and_auditor_only`. No multi-tenant admin delegation is implemented. |
| An operator silently changes or removes a posted ledger/audit row | PostgreSQL triggers reject UPDATE/DELETE; app database role has only SELECT/INSERT on those tables. A SHA-256 checkpoint can be stored separately to detect later changes to its event prefix. | `tests/test_money.py::test_financial_and_audit_rows_are_database_append_only` and `tests/test_money.py::test_audit_checkpoint_is_stable_and_detects_record_changes`. A database owner can alter triggers; the checkpoint is manual and depends on separate storage. It is not cryptographic tamper evidence if the database and checkpoint are both controlled by the attacker. |
| A privileged database operator rewrites ledger data or breaks entry order | Every ledger entry includes a SHA-256 digest of its canonical fields and previous digest. The runtime appender serializes writes with a transaction advisory lock; the public verifier recomputes the chain and balance totals. | `tests/test_money.py::test_ledger_entries_form_a_chain_and_public_endpoint_checks_parity` and `tests/test_stride.py::test_tampering_update_to_ledger_entry_is_rejected`. A database owner can disable guards and rewrite both data and chain; retain verifier results or checkpoints outside the database for stronger evidence. |
| Request forgery triggers movement in a signed-in browser | Session CSRF token is required on POST forms; login uses a short-lived double-submit token; cookies are HttpOnly and SameSite=Lax. Production mode sets Secure cookies. | Invalid transaction tokens are audited; account-create and logout CSRF behavior have direct integration tests. There is no automated browser CSRF flow test. |
| Session token is guessed or stolen from the database | 256-bit random cookie token; only SHA-256 verifier is stored server-side; 12-hour server expiry; logout deletes the session. | No MFA, suspicious-session alerts, or forced global revocation UI. HTTPS is required in deployment. |
| Concurrent transfers lock accounts in opposite order | All involved account IDs are sorted before locks are acquired. | Reduces the common transfer deadlock cycle; deadlocks can still arise from other database work and need retry/monitoring policy for a larger system. |
| Invalid amount or insufficient funds is hidden from the statement | Refused attempts are stored in the append-only audit event stream with actor, reason, requested amount, and locked balance when the account exists. | GET /accounts/{id} displays refused attempts. Malformed CSRF/parser failures have less context than normal service-level refusals. |
| Extreme numeric notation causes excessive amount conversion work | The HTTP route accepts only a short ASCII INR decimal and checks the maximum before converting it to integer paise. | `tests/test_money.py::test_transaction_rejects_extreme_decimal_exponent_before_integer_conversion`. |
| Password guessing against one username from one client address | Five failures in a 15-minute window block the username/address pair for 15 minutes; counters live in PostgreSQL and are shared by app instances. | `tests/test_money.py::test_login_throttle_blocks_after_five_bad_passwords`. Distributed attempts from multiple addresses can evade this control; there is no MFA or alerting. |
| A pending or rejected holder moves funds, or an operator fails to stop a compromised account | Holder transactions require approved KYC and both source/destination accounts must be unfrozen. Admin KYC and freeze transitions are CSRF-protected and audited. | `tests/test_money.py::test_pending_kyc_holder_cannot_move_funds`, `tests/test_money.py::test_admin_kyc_review_is_csrf_protected_and_audited`, `tests/test_money.py::test_frozen_account_rejects_movement_and_admin_can_unfreeze`, and `tests/test_stride.py::test_elevation_of_privilege_auditor_cannot_freeze_accounts`. Admin/database-owner compromise remains a trust boundary. |
| Login-throttle table growth from many unique username/address pairs | Bucket keys contain a SHA-256 digest; stale rows are pruned in batches during successful or failed credential checks. | There is no global request/IP quota, so a distributed source can still create many recent buckets. Monitor database storage before production use. |
| Audit storage exhaustion | Not addressed by this prototype. | Audit rows are retained indefinitely; set up storage monitoring, retention policy, and archival before production use. |
| Public ledger verification is repeatedly requested to consume database/CPU capacity | The endpoint returns only aggregate integrity results and is intended for the challenge-sized ledger. | Verification is O(number of ledger entries) and has no dedicated request quota; add shared rate limiting or a scheduled signed verification snapshot before scaling. |
| SQL injection or reflected input | SQLAlchemy parameterized expressions; Jinja HTML autoescaping; no raw user-generated SQL. | No dedicated injection or XSS test suite yet. |

## STRIDE regression suite

`tests/test_stride.py` has one database-backed regression test for each category: spoofed sessions (S), ledger mutation (T), refusal audit evidence (R), cross-holder statement access (I), login throttling (D), and auditor privilege escalation (E). These tests cover the listed abuse cases, not every possible attack within each STRIDE category.

## Invariants

1. Every transfer has postings whose signed amounts sum to zero.
2. An account's cached balance changes in the same transaction as its ledger posting.
3. An account balance never becomes negative through the movement service.
4. A given actor/key pair can produce at most one committed result.
5. A holder can move money only from accounts owned by that holder; transfers also require ownership of the destination.
6. The web application's database role cannot update or delete ledger or audit rows.
